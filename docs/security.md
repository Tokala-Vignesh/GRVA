# Local Security Architecture & Hardening Guide

## 1. Threat Model & Design Philosophy

**CloudSentinel AI** is an enterprise-grade desktop application designed for single-user, local-first operation. Because it connects directly to live cloud environments (AWS, GCP, Azure, and private servers) and handles infrastructure credentials, defense-in-depth local security is applied at every layer.

### Core Security Guarantees:
1. **Zero External Backend / Zero Telemetry Phoning Home**: The application never transmits your cloud credentials, infrastructure metrics, logs, or agent conversation history to external third-party hosts, Supabase, Firebase, or external telemetry collectors.
2. **Strict Loopback Binding**: The Python backend binds exclusively to IPv4 loopback `127.0.0.1`. Binding to `0.0.0.0` or public network interfaces is strictly prohibited.
3. **Ephemerally Generated API Session Token**: Every application launch generates a cryptographically secure 32-byte hexadecimal token (`X-CloudSentinel-Token`). The backend rejects any API request lacking or presenting an invalid token with HTTP 401 Unauthorized.
4. **OS-Native Keyring Credential Vault**: Cloud access keys, client secrets, and service account keys are stored in the operating system's native secure credential manager (Windows Credential Manager, macOS Keychain, Linux Secret Service).
5. **No Plaintext Secrets in Database**: The SQLite database stores only non-sensitive connection metadata and credential references (`vault://...`).

## 2. Desktop Shell Security (Electron)

The Electron desktop shell (`desktop/main/main.ts`) implements the Electron Security Checklist recommendations:

- **Context Isolation Enabled**: `contextIsolation: true` prevents renderer scripts from accessing Electron or Node.js internal objects.
- **Node Integration Disabled**: `nodeIntegration: false` ensures renderer code cannot execute arbitrary Node.js APIs or native child processes.
- **Sandboxed Renderers**: `sandbox: true` runs renderer processes within OS-level process sandboxes.
- **Navigation Lockdown**: Arbitrary URL navigations (`will-navigate`) and new window requests (`setWindowOpenHandler`) are blocked. Only trusted internal URLs are permitted.
- **Strict Content Security Policy (CSP)**:
  ```http
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  font-src 'self' data:;
  connect-src 'self' http://127.0.0.1:8765 http://127.0.0.1:11434;
  ```
- **Hardened Preload Bridge**: `desktop/main/preload.ts` exposes only an immutable, typed `window.cloudSentinelDesktop` interface with sanitized IPC channels.

## 4. Safe Controlled Remediation Guardrails

CloudSentinel AI never performs destructive cloud operations automatically. All remediation proposals adhere to strict safety guardrails:

- **Whitelisted Actions Only**:
  - `recommend_resize` (Advisory capacity scaling recommendation)
  - `send_notification` (Slack/Webhook/Desktop alert dispatch)
  - `restart_service` (Private server systemd restart)
  - `restart_container` (Docker container restart)
- **Forbidden Destructive Actions**:
  - Deleting or terminating EC2 instances, GCP VMs, or Azure Virtual Machines
  - Dropping or deleting production databases (RDS, Cloud SQL)
  - Modifying VPC routing tables or deleting internet gateways
  - Modifying IAM root permissions or deleting access policies
- **Human-in-the-Loop Approval Required**:
  - Remediations generated by the AI agent system are paused with `interrupt_before=["remediation_agent"]`.
  - The action must be explicitly reviewed and approved by the user in the UI.
  - Every remediation attempt is permanently recorded in the immutable `audit_logs` table.
